# 修改核心数据结构语义时必须跑完整语义回归测试

**发现日期**：2026-07-29  
**来源任务**：全局代码审查发现核心数据结构拷贝语义修复引入的副作用

## Rule

修改核心数据结构（如张量、存储、节点、元数据对象）的拷贝/移动/析构/共享语义时，验证不能止步于“修复目标是否达成”，必须额外运行覆盖该数据结构所有 copy/move/lifetime 相关语义的完整回归测试，特别是原先依赖深拷贝/独立实例/引用隔离的测试。

## When

- 修改 `Storage` / `Tensor` / `Node` 等核心类的拷贝构造函数、拷贝赋值、移动构造函数、析构函数；
- 将深拷贝改为浅拷贝 / 共享指针 / 引用计数；
- 改变梯度、数据、元数据等子对象的拷贝或共享策略；
- 修改影响对象生命周期的智能指针持有关系；
- 修改 allocator / deleter 行为，使得同一内存被多个对象视图共享。

## Because

1. 核心数据结构语义变更往往是“一因多果”：修复某个 bug（如后端异步写入未同步）的同时，可能悄悄改变其他模块依赖的不变量（如自动微分梯度独立性）。
2. 人类注意力容易锚定在“修复目标”上，产生确认偏误，忽略副作用测试。
3. copy/move/lifetime 相关测试通常已经编码了该数据结构的历史契约；如果这些测试失败，说明契约被违反，而不是“测试过时”。
4. 在训练数据中，只验证修复目标而不验证完整语义的轨迹会鼓励模型未来继续采用“最小验证”策略，导致系统性回归风险。

## Verification

- 列出所有涉及该数据结构 copy/move/lifetime 的单元测试，并全部运行通过。
- 重点检查以下语义契约：
  - 拷贝后两个实例是否独立修改互不影响（deep-copy invariant）
  - 共享/浅拷贝是否显式文档化，且仅在预期路径下发生
  - 析构后是否有其他对象持有悬空指针或引用
  - 移动后原对象是否处于合法 but unspecified 状态
  - 子对象（如梯度、数据）的生命周期是否被正确管理
- 若既有测试覆盖不足，优先补充测试而非跳过验证。
- 使用反事实实验 (CFC)：若保持原语义，修复目标是否仍可达？若必须改变语义，是否有更小侵入的替代方案？

## Failure cases

- 仅运行端到端准确率测试就宣布修复成功，忽略梯度独立性测试失败。
- 以“性能优化”为由将深拷贝改为共享，但不更新依赖独立拷贝的测试与文档。
- 发现既有测试失败后，不修复 bug 而是修改测试来适配新语义（除非经过 HITL 并显式文档化语义变更）。
- 将“编译通过”等同于“语义正确”。

## Future scenarios

- 任何类似“张量 + 元数据 + 梯度”三段式结构，拷贝语义变更时都应运行完整回归。
- 在引入 COW（Copy-on-Write）、共享 buffer、视图（view）与副本（copy）区分时，此规则尤其关键。
- 未来修改 allocator、自定义删除器、设备迁移 `to()` 等操作时，必须回归所有 copy/move/lifetime 测试。
- 适用于任何使用引用计数或共享内存的 C++ 框架，不局限于 HPC。
