> 适用：撰写 ADR、设计提案、README、迁移指南、API 文档、会议纪要、复盘报告、博客/对外技术文章。

## 1. 阶段一：读者与目标锚定 (R)

### 1.1 (CTX) 复述模板

```markdown
(CTX) 文档类型：<ADR / 提案 / README / 迁移指南 / 会议纪要>
(CTX) 目标读者：<初级开发者 / 核心维护者 / 外部用户 / 管理层>
(CTX) 核心目标：<传递决策 / 指导使用 / 记录过程 / 争取资源>
(CTX) 约束：<篇幅 / 格式 / 保密性>
(CTX) 硬约束：<来自项目 memory 的约束>
```

### 1.2 读者模型

```markdown
(READER_MODEL)
- 读者已知：...
- 读者未知但必须知道：...
- 读者可能误解的点：...
- 读者读完后的预期行动：...
```

---

## 2. 阶段二：内容结构与论证 (T)

### 2.1 结构化大纲

```markdown
(T) 文档结构
  ├── 背景与问题
  ├── 目标
  ├── 约束
  ├── 方案对比（如适用）
  ├── 决策与理由
  ├── 实施步骤（如适用）
  ├── 风险与回滚
  ├── 相关链接
  └── 附录
```

### 2.2 证据分级

文档中的每个断言必须标注证据等级：

```markdown
- (F0) 直接观察 / 测试输出
- (F1) 代码阅读得到的直接语义
- (F2) 文档 / 注释声明
- (F3) 间接推断
- (F4) 模型先验 / 常见模式
```

禁止将 F3/F4 当作 F0/F1 写入文档正文而不加限定。

### 2.3 反事实与边界

```markdown
(CFC) 若读者未采用推荐方案，文档是否提供了足够信息做决策？
(CFC) 文档是否遗漏了反对意见？
(CFC) 哪些声明在边界条件下不成立？
```

---

## 3. 阶段三：起草与最小验证 (E)

### 3.1 最小可用文档

先完成以下部分，再扩展：

1. 一句话摘要
2. 决策 / 结论
3. 关键理由（带证据）
4. 下一步 / 行动项

### 3.2 可读性验证

```markdown
(EXP) 可读性检查
- 请一位假想目标读者阅读
- 标记所有未定义术语
- 标记所有需要跳转才能理解的引用
- 检查是否存在长段落（>5 行）和长句（>30 字）
```

### 3.3 事实核查

```markdown
(EXP) 事实核查
- 所有代码路径引用是否准确？
- 所有性能数据是否有来源？
- 所有版本号、commit hash 是否正确？
```

---

## 4. 阶段四：审查与发布 (M)

### 4.1 自审查清单

```markdown
- [ ] 开头即结论，而非背景铺垫
- [ ] 每个段落只讲一个点
- [ ] 技术术语首次出现已解释
- [ ] 图表/代码块有标题或说明
- [ ] 反对意见已被正视而非回避
- [ ] 行动项有负责人和截止时间
```

### 4.2 子 Agent 审查（强制）

```markdown
(SUB) [YYYY-MM-DD HH:MM:SS] FORM_REVIEWER | 文档格式审查
输入: 当前文档草稿
约束: 检查结构、术语一致性、可读性

(SUB-OUTPUT) [YYYY-MM-DD HH:MM:SS]
...

(SUB-VERDICT) [YYYY-MM-DD HH:MM:SS]
- 采纳: ...
- 拒绝: ...
```

## 5. 阶段五：对抗思考 (ADV)

```markdown
(ADV) 文档是否过度推销某个方案而弱化风险？
(ADV) 是否存在可被对手方攻击的薄弱论证？
(ADV) 若读者只读摘要，是否会做出错误决策？
(ADV) 文档是否会在 6 个月后过时？如何降低维护成本？
```

## 7. (HITL) 决策门

以下情况必须停止并请求人类确认：

1. 文档将对外发布或代表项目官方立场。
2. 文档中固化架构决策或工程规范。
3. 文档涉及未公开的漏洞、性能数据或商业敏感信息。
4. 文档将替代已有官方文档。
5. 文档中的决策与既有 MEM 冲突。

### 7.1 HITL_REJECTED 记录

若人类否决了文档结构、结论表述或发布计划，必须按 master-prompt 要求记录完整 `(HITL_REJECTED)` 轨迹。
