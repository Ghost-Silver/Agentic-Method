## 2. 阶段二：多方案结构化设计 (T)

### 2.1 设计空间枚举

至少提出 **3 个候选方案**，每个方案标注置信度：

```markdown
(BRANCH) 方案 A：最小改动 (CONF: medium, F1×1, F3×1)
- 改动点：
- 优点：
- 缺点：
- 风险：

(BRANCH) 方案 B：中等重构 (CONF: medium, F1×2, F3×1)
...

(BRANCH) 方案 C：激进重构 (CONF: low, F4×1)
...

(MERGE) 推荐方案：<理由 + 置信度>
```

### 2.2 评估维度

```markdown
| 维度 | 权重 | 方案 A | 方案 B | 方案 C |
|---|---|---|---|---|
| 正确性 | 高 | | | |
| 性能 | 高 | | | |
| 可维护性 | 中 | | | |
| 实现成本 | 中 | | | |
| 回滚成本 | 低 | | | |
| 对现有测试影响 | 高 | | | |
| 综合置信度 | - | | | |
```

综合置信度必须基于原型实验数据，禁止纯理论给出 high。

### 2.3 反事实推理 (CFC)

对每个方案追问：

```markdown
(CFC) 若该方案在半年前实施，是否能避免当前痛点？
(CFC) 若该方案撤回，系统是否能快速回退？
(CFC) 该方案是否引入了新的隐藏假设？
(CFC) 该方案是否放大了时序 / 同步 / 内存风险？
```

### 2.4 原型实验 (EXP)

架构决策必须通过原型验证，禁止纯理论推导：

```markdown
### EXP-1：性能原型
- 方法：在最小可运行版本上实现候选方案核心路径
- 指标：端到端延迟、吞吐、内存占用

### EXP-2：正确性原型
- 方法：运行现有测试套件 + 新增边界测试
- 指标：全部通过

### EXP-3：回滚原型
- 方法：验证是否能在 1 小时内回滚到原架构
- 指标：可回滚
```

## 3. 阶段三：方案实施 (E)

### 3.1 渐进式重构原则

1. **小步提交**：每次只完成一个逻辑单元的重构。
2. **保持测试通过**：每步提交前必须测试通过。
3. **接口兼容层**：若必须破坏接口，先引入兼容层并标记废弃。
4. **双写验证**：新旧实现并行运行，对比输出一致性。

### 3.2 架构改动记录

每次改动必须记录：

```markdown
## [timestamp] E | 架构改动
- 改动文件：
- 改动原因：
- 影响接口：
- 测试验证：
- 回滚命令：
```

## 5. (HITL) 决策门

1. 任何破坏 ABI / 公共接口 / 序列化格式的决策必须确认。
2. 任何影响调度优先级或执行模型的决策必须确认。
3. 任何需要大规模删除或重写已有模块的决策必须确认。
4. 架构方案选择必须通过原型实验数据支撑后才能确认。
5. 推荐方案综合置信度为 low 时必须确认。
